# Golden traces

Golden traces record what the vanilla 26.3 client does, tick by tick, in scripted scenarios: the inputs it reads, the packets it sends, the packets it processes and the player's state after every tick. Ruthenium's simulation will replay the inputs and inbound packets and must reproduce the positions, velocities and outbound packet bytes exactly.

The committed traces are in `tests/golden/26.3/`. `crates/ruthenium-trace` reads them. Its tests check every trace against vanilla's per-tick packet rules and check every recorded packet id against the ids `cargo xtask codegen` generated.

## Recording

```sh
cargo xtask trace                      # all scenarios into cache/traces/26.3
cargo xtask trace --only ice,swim      # some of them
cp cache/traces/26.3/*.jsonl tests/golden/26.3/   # update the committed traces
```

Each run empties `cache/traces/26.3` first, so copy the traces to keep before recording others.

A game window opens for about 90 seconds. The client runs from your own 26.3 install (found like `ruthenium locate` does), with Mojang's Java runtime from that launcher, in offline developer mode (`--offlineDeveloperMode`): singleplayer only, and your account is never used.

On top of vanilla it loads:

- **Fabric Loader** 0.20.1;
- **Fabric API's client gametest module** and the two modules it needs (`fabric-api-base`, `fabric-networking-api-v1`, `fabric-resource-loader-v1`). These are not the whole of Fabric API, so no other parts of the game are replaced;
- **`tools/java/trace`**, Ruthenium's recorder: a few hooks at tick and frame boundaries, on `Connection.send` and on inbound packet processing, plus the scenarios.

All jars are pinned by SHA-1 (`xtask/src/fabric.rs`) and kept in git-ignored `cache/`.

### The test harness

Fabric's client gametests run the game in lockstep. Each client tick is one frame, the integrated server runs exactly one tick per client tick, and test code runs between ticks while both threads wait. A key pressed in a script is therefore read on a known tick, and the game-thread records (`tick`, `state`, `out`) of two recordings are identical down to every float bit. That was checked by recording every scenario twice and comparing.

Things this harness changes compared with normal play, which replay tests must allow for:

- **Frame and tick timing.** There is one tick per frame and no catch-up, so vanilla's `DeltaTracker` frame/tick timing is not exercised. Between ticks the harness also renders a few frames while test code runs. Timing tests use the simulated clocks in the plan instead.
- **Singleplayer.** The connection is the integrated server's in-memory one. The recorder encodes each packet itself with the protocol in effect, which gives the same bytes the network encoder would write before framing, compression and encryption.
- **Inbound arrival.** Packets from the server arrive on the network thread at times that vary from run to run. `recv` records and the tick on which a `handle` happens (for example `set_time`, sent every 20 server ticks) can differ between recordings. Each trace records where they actually happened, which is what a replay needs.

## Replaying

`crates/ruthenium-sim/tests/golden.rs` replays every trace through Ruthenium's movement code: it builds the scenario's world from the header's commands on the flat preset, applies the packets the client handled (entities added, moved and removed, their data, teams, the player's motion, teleports and attributes, the player's own entity data, abilities, effects, operator level and game mode, from the game event and from its player-list entry, which the header's `playerUuid` names, its inventory, item cooldowns, food and the server's "item use complete" event, and block updates and block-change acknowledgements through the client's predictions) where the trace handled them. Items the header's `build` commands gave (`item replace`) start in the inventory. Then each tick it sets the camera's rotation and the selected slot, sends the held slot if it changed, picks what the crosshair is on, plays the recorded hotbar, use, swap-hands and attack presses and the held use and attack keys through the client's item use, attacks and block breaking (both hands, the items' own predictions, the server's echo of the use, the miss penalty, the attack strength and the attacker's own slowdown, the breaking progress and the predicted removal of the broken block), holds the recorded movement keys, runs the entities' tick with the player's in its place, and compares the position, velocity, ground and collision flags, sprinting, pose and flight with the `state` record (and, where the record has them, what the crosshair is on, the item in use, the hands, the food level and the block being broken: its position and state, the progress, ticks and delay, bit for bit), and the packets the tick sends (`set_carried_item`, `player_loaded`, `client_command`, `attack`, `punch`, `spectator_action`, `player_action`, `interact`, `use_item_on`, `use_item`, `player_abilities`, `player_input`, `player_command`, `move_player_*`) with the `out` records, byte for byte. The prediction sequence starts one before the trace's first predicted action (`use_item`, `use_item_on`, or a `player_action` that starts or finishes breaking a block). Where the trace has `set` records, each tick's blocks set while an action was predicted (the placed block, the neighbours' shape updates, a door's top half, a button pressed...) must match them call for call: position, state, flags and update limit. Deaths and respawns are replayed too. The dying player takes no input and is taken out of the level 20 ticks later (it then stops ticking and sending). The death screen opens on the death packet; when it is open the keys are let go and the player's key binds aren't handled. The respawn requests are compared with vanilla's: those sent from `Gui.tick` within a tick, and those sent outside a tick, while handling the death packet or when the death screen's button is pressed (it must be open and working). A respawn brings a new player, which waits for the level to load: the trace's `loaded` says when, and `player_loaded` is compared. On that tick, the keys physically held (`physical`) are read again as the level loading screen closes. The `state` record's `deathTime`, `removed` and death screen are compared too. Elytra flight and riptide are replayed through the same code: the glide the client starts and the server's entity data ends, a firework rocket the server adds attached to the player and the client ticks in its place among the entities (boosting the gliding player), the knockback of the server's `explode` packets (wind charges), and a riptide trident's launch as the use key is let go, with the strength its enchantment gives (vanilla's enchantments from the jar, in the registry's order). The `state` record's `fallFlying`, `autoSpin` (the server's spin flag) and `spinTicks` are compared where the record has them. Pistons and shulker boxes run as the client runs them: the server's block events make the client work out a piston's push itself (the blocks it moves, the moving blocks and their block entities, the head), the moving blocks tick after the entities, before the player sends its movement, pushing the player ahead of them (at most 0.51 an axis in a game tick), slime launching it and honey carrying it, and a shulker box's lid lifts or pushes it as it opens. Where a trace has block events, every block the client sets outside a prediction (the block events' and the block entities' own) must match the `set` records too, call for call. Riding is replayed as the client rides: the passengers the server sets (a boat turns the player to its heading as it mounts), the player ticking after its vehicle and seated where the vehicle says (a boat turns it with itself and keeps its look within 105 degrees of its heading, a rearing horse lifts it), and a vehicle the player controls moving on the client: a boat floating, paddling and turning with the keys of the player's last tick (water, under water, land friction, air, bubble column events), a saddled horse or donkey steered by the player's input with its speed and jump attributes (or the type's defaults the server never sent), charged jumps and rearing, a camel sitting and getting up by the game time (the record's `gameTime`, as the tick runs), sprinting and dashing, a harnessed happy ghast flying where the player looks, a saddled pig or strider following the look of a rider holding its item on a stick (boosts, a strider's warmth and its walk on lava), a tame saddled nautilus swimming along the look and dashing; pistons push it too. A teleported vehicle the player steers keeps the player's own motion, not its own (`getKnownMovement`). Minecarts are the server's to move: the client follows them. The player sends its rotation each tick and the vehicle's place (`move_vehicle`), and the boat its paddles (`paddle_boat`), compared byte for byte, as are the `move_vehicle` answers the client sends outside a tick to the server's vehicle teleports and corrections. A passenger ignores the server's position packets. Clicking a boat, a horse, a camel, a saddled pig or strider or a tame nautilus with nothing in hand takes the click (the off hand isn't tried). The `state` record's vehicle, the bottom vehicle's position, motion, heading and ground flag and the horse jump's charge are compared where the record has them. It needs the prepared game (block shapes, hardness, behaviour and item classes from the exporters, the items' default components from the data generator's reports, every block and item tag, the block transformers and the enchantments from the jar):

```sh
RUTHENIUM_GAME_DIR=~/.local/share/ruthenium/game cargo test -p ruthenium-sim --test golden -- --nocapture
```

Without `RUTHENIUM_GAME_DIR` it is skipped. `RUTHENIUM_TRACES=boat_land,horse_ride` replays only those, and `RUTHENIUM_TRACE_DEBUG=1` prints where each try of the heartbeat count (below) went wrong. `crates/ruthenium-sim/tests/mouse.rs` needs nothing but the committed trace and runs everywhere: it feeds `mouse_turn`'s cursor moves through the client's own mouse path (the first motion after a grab dropped, motion summed per frame, vanilla's sensitivity curve, `Entity.turn` in floats) and checks every recorded yaw and pitch bit for bit. The scenarios listed in `EXACT` must match every tick; the others are reported. The trace doesn't record how many ticks had passed since the last position packet when it starts, so the replay tries each count until the first heartbeat lines up.

They are defined in `tools/java/trace/src/dev/ruthenium/trace/Scenarios.java`. To add one, add an entry there and record again. Scripts can run server commands while the trace records, so entities a scenario needs are summoned inside its script: their packets are then in the trace. A scenario that leaves mobs behind must remove them and wait until they are gone (dying mobs push for 20 ticks, and a large slime splits), or they push the player before the next trace starts.

## Format (`ruthenium-trace/1`)

JSON Lines. The first line is the header; every other line is one record with a kind `k`.

- **Ticks and frames.** `n` is the client tick within the trace (0 is the first recorded tick, -1 before it) and `f` is the frame.
- **Exact floats.** Floats and doubles are written in Java's shortest round-trip form. Parse the text directly as `f32` / `f64`, as `ruthenium-trace` does, to get the exact value.

| `k` | When | Fields |
|---|---|---|
| `header` | first line | `format`, `game`, `protocol`, `scenario`, `description`, `world`, `reset`, `build`, `teleport`, `options` (toggle sprint/crouch, auto-jump, mouse sensitivity), `entityId`, `playerName` (the offline player's name, which teams list), `playerUuid` (its player-list entry), `showDeathScreen` (whether dying opens the death screen, which the `immediate_respawn` game rule turns off), `harness` |
| `frame` | start of each client frame | `f` |
| `tick` | start of each client tick, before the game reads input | `n`, `f`, `down` (key mappings held), `physical` (the keyboard keys physically held, which closing a screen reads back into the mappings), `clicks` (queued presses of keys the game reads as clicks: attack, use, pick, drop, swap, inventory, hotbar), `yRot`, `xRot`, `slot` |
| `state` | end of each client tick | `n`, `gameTime`, `pos`, `vel`, `yRot`, `xRot`, `onGround`, `hColl`, `minorHColl`, `vColl`, `vCollBelow`, `fall`, `sprinting`, `shiftDown`, `pose`, `flying`, `inWater`, `input` (the tick's movement input), `move` (move vector), `health`, `fallFlying` (gliding), `autoSpin` (the server's riptide spin flag), `spinTicks` (the spin's ticks left on the client), `deathTime`, `removed` (the client has taken the player out of the level), `loaded` (the player has loaded into the level), `screen` (the open screen's class, `""` for none), `food`, `saturation`, `using` (`isUsingItem`) and while using `useHand`, `useItem`, `useRemaining`; `main` and `off` (the hands, `id*count`, empty as `""`); `hit` (what the tick's pick found: `MISS`, `BLOCK` with `hitBlock`, `hitFace` and `hitAt`, `ENTITY` with `hitEntity` and `hitAt`); breaking: `destroying`, `destroyPos` (kept after breaking ends), `destroyState` (the block state id there now), `destroyProgress`, `destroyTicks`, `destroyDelay`; riding: `vehicle` (the entity ridden), `vRoot` (the bottom vehicle) and its `vPos`, `vVel`, `vYRot`, `vXRot`, `vOnGround`, `vHColl`, `vVColl` and `vControlled` (the client moves it); `jumpScale` (a horse jump's charge) and `handsBusy` |
| `out` | every serverbound packet, as the game hands it to the connection | `n`, `f`, `thread` (`game` or `net`), `inTick`, `proto`, `name`, `hex` (packet id VarInt and payload) |
| `recv` | a clientbound packet arriving, on the network thread | `n`, `f`, `thread`, `proto`, `name` |
| `handle` | a clientbound packet being processed on the game thread (sub-packets of a bundle get `bundled: true`) | `n`, `f`, `thread`, `proto`, `name`, and `hex` for packets that affect the local player |
| `set` | a block the client level sets (`ClientLevel.setBlock`), as the call is made: predicted by an action, restored by an acknowledgement or updated by the server | `n`, `inTick`, `pos`, `state` (state id), `flags` (`Block.UPDATE_*`), `limit` (the update limit), `predicting` |
| `end` | last line | `ticks` |

Inbound bytes are recorded only for the packets that affect the local player or its surroundings in a scenario: position and rotation, motion, explosions, attributes, effects, abilities, health, game events, tick rate, held slot, keep-alive and ping, damage, entities added and removed, their data, movement and passengers, teams, the player list, block updates, block events and acknowledgements, inventory slots, item cooldowns, sounds, the server's vehicle moves. Chunk, light, registry, tag, recipe and advancement packets appear by name only, so traces hold Ruthenium's own measurements and no game data (see `docs/reference-policy.md`, rule 5).
